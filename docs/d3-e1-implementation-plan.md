# DOGWOOD-SHARP-D3 implementation plan

Status: **proposed, not authorized**. This plan follows the D3-E1 compatibility
decision **B** and is bounded to the Cedar evaluation layer. It does not
authorize temporal execution, providers, packaging or a stable public API.

Entry conditions:

- D2 is accepted and closed. See [the D2 acceptance record](d2-acceptance.md).
- The D3-E1 evidence is accepted. See
  [the compatibility report](d3-e1-compatibility.md) and
  [verification record](d3-e1-verification.md).
- The implementation commission names the supported RIDs and TFMs. D3-E1
  executed only Windows `win-x64`; Linux and macOS remain pending.

## 1. Objective

Provide an explicitly experimental CedarSharp-backed Cedar evaluation path for
validated Dogwood lowering output, without changing CedarSharp and without
weakening the D2 bridge's lifetime, validation or temporal boundaries.

The deliverable is an adapter that:

1. Takes a complete, validated D2 lowering result and a caller request.
2. Constructs the policy set, schema, context and entities with stable Dogwood
   rule identity.
3. Calls CedarSharp and returns the raw decision, determining rule identities,
   policy errors and operation errors.
4. Applies an explicit clean-Allow or fail-closed policy at the adapter
   boundary.
5. Keeps trusted temporal/provider values out of caller control.

## 2. Design constraints carried from D3-E1

| Constraint | Consequence |
| --- | --- |
| Cedar policy IDs are generated by Dogwood and must survive. | Use an ID-to-body policy set. Never reparse concatenated text for identity. Never treat a source `@id` annotation as the stored ID. |
| The prototype splitter depends on source-order insertion. | Add a per-rule export before production. Do not ship the splitter as a contract. |
| The augmented schema carries the action hierarchy. | Every request must carry the schema. Do not rely on synthesizing or transporting action entities. |
| Upstream injects bare scope entities; CedarSharp does not. | Reproduce the three-tier entity-store construction or explicitly define and test the different mode. |
| A raw Allow can carry policy errors. | Expose the raw decision and errors; enforce a separate clean-Allow decision for enforcement callers. |
| The temporal generated field is authoritative only inside the trusted pipeline. | Reserve generated names; reject caller-supplied reserved fields; compute values before the call and deny closed on failure. |
| Both native images must remain resident for process lifetime. | No unload, hot replacement or collectible-context reclamation promise. Document process isolation as the replacement path. |
| CedarSharp has no callback seam. | Materialize an immutable request snapshot; do not design lazy provider callbacks into CedarSharp. |

## 3. Work packages

Each package is independently reviewable. A later package may not claim an
earlier package's evidence.

### D3-1: ID-stable per-rule export

Scope:

- Add a bridge operation or extend the existing lowering result so each Dogwood
  rule returns its exact Cedar body and its generated Cedar policy ID in one
  record. The export must be complete or fail; no partial success.
- Keep the existing concatenated `CedarPolicyText` for compatibility. Do not
  remove or reinterpret it in D3.
- Preserve the distincter and ID-generation behavior. Source `@id` annotations
  remain annotations and never become stored policy IDs.
- Add bounded-size accounting to the new reply under the existing D2 response
  ceiling discipline.

Tests:

- One rule; many rules; duplicate-ID rejection; empty policy set policy.
- Escaped quotes, backslashes and Unicode in entity IDs and annotations.
- Semicolons inside strings, braces and nested records.
- Exact reconstruction: joining the exported bodies in rule order reproduces
  the existing concatenated text, or the operation fails.
- Every body parses on CedarSharp and on the pinned reference.
- Distincter and source-annotation controls.

Exit criteria: the managed adapter can build a policy set without splitting
text, and a test proves every returned ID maps to exactly one Dogwood rule.

### D3-2: Adapter core and error identity

Scope:

- Add an experimental namespace, for example
  `DogwoodSharp.Experimental.CedarSharp`, containing an adapter type and its
  request/result records. Mark it experimental and non-packable until D3 passes
  its gate.
- Accept only a complete validated lowering result. Reject missing artifacts,
  empty schemas when required and mismatched rule counts before dispatch.
- Build `CedarPolicySet.FromPolicies`, `CedarSchema` and
  `CedarAuthorizationRequest`.
- Map determining and erroring Cedar IDs to Dogwood rule identities by
  identity. Unknown IDs are an adapter failure, not a silently dropped result.
- Preserve raw decision, `IsCleanAllow`, per-policy errors and operation errors
  in the adapter result.
- Define explicit behavior for a raw Allow with policy errors: reject for
  enforcement callers, expose for diagnostic callers.

Tests:

- The full E1 corpus through the adapter.
- Twelve distinct IDs; ID order independence; unknown-ID injection.
- Clean Allow, raw Allow with a policy error, errored forbid, operation
  failure, malformed policy set.
- Negative control: a valid permit beside an unparsable policy never yields an
  Allow.

Exit criteria: the adapter result classifies every E1 case identically to the
direct CedarSharp call and never reports a clean Allow when a policy error is
present.

### D3-3: Entity-store construction

Scope:

- Reproduce the upstream three-tier store: schema-check caller entities, inject
  bare scope principal/resource when absent, merge schema action entities as
  upstream does.
- Decide explicitly whether the adapter promises upstream-authorizer
  equivalence or a documented direct-Cedar mode. Both may exist, but the choice
  must be visible in the result and in the API contract.
- Preserve `__entity`, `__extn`, parents and exact entity attributes.
- Reject caller-supplied entities that fail schema conformance before the Cedar
  call, matching upstream fail-closed behavior.

Tests:

- Bare scope identity comparison; absent scope entity attribute read;
  present-but-attribute-less scope entity; incomplete supplied entity.
- Parent edges and action hierarchy with the schema attached.
- Mixed supplied and bare entities.
- Differential against the upstream Dogwood authorizer for these cases, not
  only the Cedar FFI. This is a new oracle requirement; E1 did not execute it.

Exit criteria: the chosen store mode is observable, tested and documented, and
no case silently changes an absent entity into a present one or vice versa.

### D3-4: Schema and request conformance

Scope:

- Carry both schema representations as exported; use one for the call and keep
  the other available for diagnostics.
- Validate that the schema used for authorization is the same revision as the
  one used for policy validation.
- Define request-validation behavior. Keep `validateRequest` as an explicit
  caller choice only if the public contract can explain it; otherwise fix the
  adapter to the safer mode.
- Preserve context extension encodings. Do not coerce decimals, datetimes or
  IP addresses to strings.

Tests:

- All E1 cases on both schema forms.
- Validation warning/error parity.
- Missing required context attribute.
- Invalid principal/resource type with request validation on and off.
- Schema revision mismatch control.
- `ipaddr`, `decimal`, `datetime` boundaries and invalid extension values.

Exit criteria: schema form and request-validation mode cannot change the
decision except where the documented contract says they do.

### D3-5: Temporal and provider boundary

Scope:

- Reserve generated context field names for the trusted pipeline.
- Reject caller-supplied reserved fields at the adapter boundary.
- Wire the adapter behind Dogwood's trusted temporal/provider pipeline; do not
  expose the manual context injection used by the E1 harness.
- Define fail-closed behavior when temporal evaluation or a provider fails.
- Keep temporal bindings internal; do not serialize authoritative booleans into
  a caller-visible request type.

Tests:

- The E1 temporal case with true and false values computed by the trusted
  pipeline.
- Caller attempts to supply a reserved field; must reject.
- Temporal evaluation failure; must deny closed with a classified error.
- Provider failure and missing provider value.
- Cross-request isolation of generated fields.

Exit criteria: no public path lets caller context stand in for a temporal
evaluation, and the trust boundary has a dedicated negative-control suite.

This package may depend on D4. If D4 is not authorized, D3-5 remains a design
and test harness only.

### D3-6: Lifecycle, AOT and concurrency

Scope:

- Keep the D2 bridge and CedarSharp native images resident for process
  lifetime. Reject custom load contexts and unload expectations.
- Publish a NativeAOT consumer that loads both images, lowers, authorizes and
  reports identities.
- Define concurrency: whether one adapter instance is safe for concurrent
  calls, or callers must serialize. Do not assume CedarSharp concurrency from
  sequential tests.
- Define disposal of managed result objects only; no native unload.

Tests:

- JIT and NativeAOT on both TFMs.
- Concurrent first access and repeated calls, with a documented worker bound.
- Custom-context rejection.
- Process-exit behavior; no manual unload.
- Failure path: missing manifest, hash mismatch, incompatible ABI.

Exit criteria: supported hosting modes are enumerated, unsupported modes fail
explicitly, and AOT execution is qualified rather than inferred from publish
success.

### D3-7: Qualification corpus and matrix

Scope:

- Expand the corpus beyond E1: open-ended policies, temporal boundaries,
  provider records, large entity sets, deep context records, malformed inputs,
  Unicode and escaping, duplicate IDs, and operation-error combinations.
- Differential against both the pinned Cedar FFI and the upstream Dogwood
  authorizer where the feature exists.
- Run the supported RID x TFM matrix. D3-E1 contributes Windows `win-x64`
  evidence only.
- Record exact source, native artifact hashes, toolchain and command lines.

Exit criteria: no unexplained parity difference; every skip or missing case is
recorded as pending, not passed; the matrix is complete for the commissioned
RIDs.

### D3-8: Independent qualification and owner acceptance

Scope:

- Package the producer evidence and hand it to an independent qualifier.
- Qualifier designs its own fixtures, consumers and oracle use; producer
  results are supporting material.
- Owner acceptance is a separate record after qualification.

Exit criteria: a qualification disposition and a separate owner decision. A
green producer suite is not acceptance.

## 4. Public API posture

No public API is added by this plan's first four packages. The experimental
adapter remains:

- outside the stable namespace;
- marked experimental in documentation;
- not packable or not included in the package until D3-8;
- free to change without compatibility promises.

A stable API requires its own design review after the adapter semantics,
entity-store mode and temporal boundary are qualified. Do not graduate the E1
prototype types (`E1Bundle`, `E1ReferenceInput`, the splitter) into `src/`.

## 5. Required gates

| Gate | Requirement |
| --- | --- |
| Restore/build | Locked restore where the RID graph permits; Release build with zero warnings on both TFMs. |
| Unit and integration | Full adapter suite, E1 corpus retained as regression, negative controls. |
| Differential | Pinned Cedar FFI and, for entity/temporal claims, the upstream Dogwood authorizer. |
| ID preservation | Every determining/erroring ID maps to exactly one rule; no positional mapping; `@id` controls. |
| Schema/entity round trip | Both schema forms; exact entities; conformance failures fail closed. |
| Temporal boundary | Reserved-field rejection; trusted-pipeline values only; fail-closed test. |
| Lifecycle | AOT on both TFMs; no unload promise; missing/mismatched artifact failures. |
| Regression | Existing D1 and D2 suites unchanged and passing. |
| Evidence | Durable report bound to the exact revision, host, RID, TFM and commands. |

## 6. Explicit exclusions

- No CedarSharp source or package change.
- No production CI change to obtain a pass.
- No full D3 implementation before authorization.
- No D4/D5 temporal execution, event store, replay or distributed coordination.
- No information providers, network providers or Hufu integration.
- No NuGet publication, tag or release.
- No cross-platform claim from Windows-only evidence.
- No performance or memory guarantee.
- No stable public API or compatibility promise.

## 7. Suggested order and stopping points

1. D3-1 and D3-2: identity and request construction.
2. D3-3 and D3-4: store and conformance semantics.
3. D3-6: packaging and lifecycle.
4. D3-7: expanded qualification.
5. D3-5 only when the temporal/provider pipeline is authorized.
6. D3-8 after the evidence is complete.

Stop after each package for review if the commission is time-boxed. The first
credible stopping point is a reviewed adapter core with ID-stable export and
the E1 corpus passing; it is not a production or package milestone.
